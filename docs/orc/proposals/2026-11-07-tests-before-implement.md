# 提案：测试和验证检查在设计之后、实现之前写好，并和计划一起签名

状态：**林翰 2026-11-07 已决定，三处都选 A**。已写进 PLAN「已确定的决定」的「验证」一行；阶段 3 已实现（见文末「实现」）。

## 要解决的问题

林翰的要求：测试、验证检查、边界这些，都要在设计结束之后、真正实现之前设置好。写测试的 agent 手上没有任何实现的上下文，这样最安全，也最不容易被带偏。

现在的计划做不到这一点：

- 规划会话在 DAG 里只写了 `verification`（一条命令，比如 `pytest tests/test_calc.py`）和验收标准的文字。
- **测试代码本身由执行会话写**。玩具 mission `toy1` 的计划就是这样：执行会话先写 `test_subtract`，再写 `subtract`。
- 结果是测试和实现出自同一个会话、同一份上下文。执行会话写的测试可能迁就自己的实现（只测自己做到了的、断言写得很宽），之后检查全部通过也说明不了什么。
- PLAN 阶段 4 里 broker 按 `checks.json` 跑检查，但没有写明 `checks.json` 由谁、在什么时候写。

边界（每个节点能改哪些文件、对外接口 `contracts`、对应的 N# 条款）已经由规划会话写进 DAG，在 go 时冻结并签名。缺的只是**测试代码和检查清单**。

## 方案

在 `planning` 之后、`plan-review` 之前加一步“写验证”：

1. **规划会话产出通过校验后**，orc 启动一个**新的、独立的会话**写验证。它只拿到：
   - 签名前的 `design.md` 和 `task-dag.json`（验收标准、`contracts`、声明文件）；
   - 产品仓库的现有代码（只读）；
   - **拿不到**规划会话的对话过程，也不会有任何实现代码（这时还没开始实现）。
2. 它的产出写在自己的工作目录里：
   - 测试文件（放进 DAG 里专门的测试路径，例如 `tests/orc/<node>/…`）；
   - `checks.json`：每条验收标准对应一个或几个检查 id，每个检查 id 是一条能直接运行的命令。每条验收标准至少要有一个检查。
3. **orc 校验**（不交给模型）：
   - 每条验收标准都有检查；检查命令能运行；
   - **在现有代码上，新写的检查必须失败**（还没实现就通过的测试，说明它什么也没测），已有行为的检查可以标成 `baseline` 并要求通过；
   - 校验不过就发回同一个会话修，最多 2 次，还不过就 `mediate`（和规划会话的规则一样）。
4. 审阅页上加一节「验证」：每条验收标准旁边列出对应的检查和测试文件。你审的时候一起看。
5. **说 go 时一起冻结、一起签名**：`approved.sha256` 里加上测试文件和 `checks.json` 的哈希。
6. 执行阶段：
   - 冻结的测试文件在执行会话里**可读、不可改**：节点的声明文件不能包含测试路径（冻结时由 `validate-task-dag.sh` 校验），broker 拒绝任何改动这些路径的提交。
   - broker 和整体评审跑检查之前，先核对测试文件的哈希和签名时一致，不一致就拒绝。
   - 执行会话可以自己另外加单元测试（放在它自己的声明文件里），但**只有冻结的检查算数**。
7. 隐藏考题不变：仍由你写，只在 CI 跑（阶段 5）。冻结的测试是公开的，执行会话能看到要达到什么；隐藏考题防的是“只为了让公开测试通过”。

## 需要你定的三处

**1. 什么时候写、怎么批准**

- **A（推荐）在 go 之前写，和设计、计划一起签一次名。** 你只需要审一次、签一次；测试一旦签名，执行阶段谁也改不了。
- B 在 go 之后、实现之前写，再审一次、再签一次名。设计可以先定下来，但多一个关口。

**2. 写验证用哪个模型**

- **A（推荐）`review` 角色的模型（目前 Fable 5.1）。** 和执行用的 Opus 不是同一个模型，盲区不一样，和“评审不能用实现的模型”是同一个道理。
- B `plan` 角色的模型（Opus），新开会话。便宜一些，但和执行是同一个模型。

**3. “新写的检查在现有代码上必须失败”要不要强制**

- **A（推荐）强制。** 每个不是 `baseline` 的检查，orc 都在现有代码上实际跑一遍，通过了就发回去改。这是防止“空测试”最直接的办法。
- B 不强制，只靠你在审阅页上看。

## 影响

- 「已确定的决定」：新增一行「验证」：测试和检查在实现前由独立会话写好，随计划一起签名，执行阶段只读。
- PLAN 阶段 3 加一步“写验证”；阶段 4 的 broker、整体评审改为只认冻结的检查，并加上哈希核对；契约测试加“改冻结测试的提交被拒”“测试哈希不一致时拒绝”。
- STATE.md：`planning` 和 `plan-review` 之间加 `verifying` 状态（或作为 `planning` 的第二步，不加新状态，实现时定）。
- `orc go`：冻结的文件从四个变成六类（加测试文件和 `checks.json`）。

## 实现（阶段 3，2026-11-07）

和上面的方案一致，另外三处细节：

- **验收测试怎么签名**：签名的哈希清单是复用脚本约定的四个文件（`validate-task-dag.sh --freeze`、`verify-approved-authority.py`、broker、integrate-task 都按四个文件校验），改它要动三个复用脚本和它们的契约测试。所以不改清单：验收测试的哈希写进 `brief-exec.md` 的「冻结的验收测试」一节，`brief-exec.md` 在清单里，签名就连带覆盖了验收测试。orc 每次 step 都按这些哈希核对 `approved-checks.json` 和 `approved-tests/`。
- **检查在沙箱里跑**：检查命令是 agent 写的，orc 用 macOS 的 `sandbox-exec` 运行：只能写那份干净的代码副本，`TMPDIR` 指向副本里面，不能联网。最初还放行了 `/tmp` 和 `/private/var/folders`，测试发现这样检查能写到别处的临时目录，已收紧。
- **代码基线**：验证会话拿到的是产品仓库当前提交的副本（提交号记在事件里）。验证期间产品仓库有新提交，orc 停下报错，因为测试是按旧代码写的。

**真实运行**（玩具仓库，mission `toy2`，请求同 `toy1`）：

- 规划会话（Opus）产出一个节点 `add-subtract`，两条验收标准。
- 验证会话（Fable 5.1）13 轮、111 秒、$2.04：新建 3 个测试文件、9 个检查（7 个 `fail`、2 个 `pass`），覆盖整数、浮点、大整数、参数顺序、关键字参数、类型错误，以及 `add` 没被改坏。
- orc 在干净副本上实际运行 9 个检查，全部符合预期：7 个在实现前失败，2 个通过；产品仓库没有被改动。
- 审阅页多了「验收测试」一节，列出每个检查和测试全文。

**已知的局限**：orc 只看退出码，判断不了检查“为什么”失败。例如 `subtract` 还不存在时，pytest 在收集阶段就报 ImportError，退出码是 4，这也算“实现前失败”。所以每个检查到底测了什么，仍要靠你在审阅页上看测试全文；之后的整体评审也会再看一遍。
