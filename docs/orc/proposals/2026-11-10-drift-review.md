## 一、检查分三类

| 类别 | 保护什么 | 怎么处理 |
| --- | --- | --- |
| **底线** | 做错了收不回，或者它本身是信任链的一环 | 保持确定性，一条不松 |
| **形状和流程** | 计划里假设的工作方式：一轮做几条、`files` 怎么写、提交说明的格式、证明材料的格式。（文件归属看起来像形状规则，实际上守着底线，见第四节） | 能删的删；不能删的改成「记下来，给评审和 PR 看」，不拦 |
| **方向** | 有没有偏离 NORTHSTAR 和设计 | 确定性检查查不了，交给偏离评审 |

orc 现在的确定性检查共 50 多条（清单见附录）。

**从数据看出的四点**

1. **来回改的 6 轮，全部来自「一轮一条验收标准」。** 这条规则只写在执行会话的 brief 里，代码并不强制，但它和冻结检查、对齐评审都对不上。
2. **全停的 3 次：** 2 次是 orc 自己的问题，1 次是文件归属规则。没有一次是评审抓到了真正的方向偏离。
3. **每次提交的对齐评审一次真正的偏离都没抓到。** 它判的 3 次 DRIFT 都是「还没做完」，而这本来就是冻结检查管的事。它还前后不一致。它平时用 `review_light`（Opus，和执行会话同一个模型），只有上一次 DRIFT 或改动超过 300 行时才升级到 Fable。
4. **上一次 DRIFT 的原因传给下一次评审时变成了乱码。** p1-1-3 第 66、145 行，评审自己说「上一次偏离原因在材料里是乱码」。这是 bug，另外修。

这批数据很小（3 次运行、1 个 mission 文件），而且都在 P1 的第一个 mission。长时间运行里方向偏离到底多常见，这批数据看不出来；偏离评审的价值是预防，不能靠这几次运行证明。

## 三、偏离评审

### 11-10 已定的

- **怎么跑：** 本机新开一个 `claude -p`，不续用任何已有会话。用 `review` 角色，模型改成 `claude-fable-5-2`（第 6 条决定）。
  - 11-10 实测：`claude -p --model claude-fable-5-2` 能正常返回，`modelUsage` 里记的就是这个模型。
  - CLI 2.1.318 会打一行 `unrecognized_model` 提示，但不影响调用。
- **只给必要的材料：** NORTHSTAR、简要设计、这次的 diff（具体见下面「材料」）。
- **只回答一个问题：** 这个 diff 有没有偏离 NORTHSTAR 或简要设计，偏在哪？
  - 不判：做没做完（冻结检查管）、小 bug（检查和 CI 管）、风格。
- **结果怎么用：**
  - `drift`：打回一次，原因写进纠偏单。第二次还是 `drift`，停下问你。节点评审和 mission 结束时的评审都按这一条（见下面「轮数」）。
  - `notes`：写进 PR 正文的「评审意见」，不拦。
  - 每次的结论和理由都记进 `events.jsonl`。

### 按评审意见补全的细节（评审第 4、7 条）

- **材料：**
  - **都给：**
    - `NORTHSTAR.md`；
    - **简要设计**：`design.md` 开头一节，40 行以内，go 时你一起签名。
      - 规划会话必须把会约束做法的东西写进这一节：分层、「不要新建 X」、错误处理策略、接口的形状。
      - 这些东西冻结测试和隐藏考题大多管不到，只能靠这一节让评审看见。
    - **画布里相关组件的一行说明**：组件 id、paths、它连着谁。这是给评审看产品层的总体设计，不给完整的产品设计文档。
  - **节点评审再加：** 这个节点的 DAG 条目（`entry.json`：组件、`files`、contracts、验收标准）。没有它，评审判断不了节点是不是在做别的组件的事。
  - **diff：**
    - 节点评审看节点的累计 diff，mission 结束时看整个 mission 的 diff。
    - 超过 60000 字节只给文件列表，让评审用 Read 看代码副本（不带 `.northstar/` 和 `.github/`），和现在的最终审查一样。
  - **不给：** 完整设计、计划、执行记录、执行会话的说明、以前的评审记录。例外：重评一次 DRIFT 时，带上次的原因。
- **输出：**

  ```jsonc
  {"verdict": "aligned" | "drift",
   "drift": [{"node": "节点 id（mission 结束时必填）",
              "rule": "N#｜简要设计第几行｜extra｜interface｜duplicate｜missing",
              "ref": "missing 时：acceptance:N 或 contract:N",
              "evidence": {"side": "tip" | "base", "file": "…", "line": 0},
              "existing": {"file", "line"},   // duplicate 必填
              "other": {"file", "line"},      // interface 必填
              "why": "…"}],
   "notes": ["…"]}
  ```

  - `rule` 除了 N# 和简要设计的行，还可以是四类：
    - `extra`：加了设计没要求的东西；
    - `interface`：节点之间接口对不上；
    - `duplicate`：重复实现已有的东西；
    - `missing`：设计里有、测试没覆盖、也没做。
    - 这四类是现在最终审查和跨 mission 评审已经在问的，不能因为只能引 N# 就漏掉。
  - 四类各自的引用要求（第二轮评审第 3 条）：
    - `missing`：节点评审只能引用**本节点** `entry.json` 里的某条验收标准或 contract（`"ref": "acceptance:2"` 或 `"contract:1"`），免得把别的节点该做的事判成本节点漏做；mission 结束时可以引简要设计的行。
    - `duplicate`：再给一条证据 `"existing": {"file", "line"}`，指向已有的那份实现。
    - `interface`：给两边的位置，`evidence` 一边、`"other": {"file", "line"}` 另一边。
    - `extra`：证据指向多出来的代码。
  - 删掉东西造成的偏离，证据在基线上：`side: "base"`。
  - orc 只确定性地核对这几件事：
    - 引的 N#、简要设计的行、本节点的验收标准或 contract 存在；
    - 每一条证据（`evidence`、`existing`、`other`）的文件和行在对应的一边存在；
    - mission 结束时，`node` 是 DAG 里的节点。
  - 核对不过就发回重写一次。第二次还不合格：不放行、不降级，停下问你，和现在其他评审一样。
- **入口（第二轮评审第 2 条，第 8 条决定）：** 偏离评审放在 orc 里，和现在的最终审查、跨 mission 评审一样，orc 自己调用 `claude -p`，不再经过信任层的 `northstar-review`。
  - 原因：`northstar-review` 只用退出码 0/1/2 表达结论，装不下带 `rule`、`side`、`node` 的输出；改它要改 `test_align.sh`，还要重新 sudo 安装。
  - `northstar-review` 留在信任层，只管 agent 自己直接提交的情况（`align.sh`），不变。
  - 从信任层搬过来、必须照样守住的三条（第三轮评审第 2 条）：
    - **模型核对（底线）：** 读 `claude -p --output-format json` 输出里的 `modelUsage`：必须出现配置的 `review` 模型，出现任何别的模型也判这次评审不可用（不放行、不降级、问你）。先这样严格做；如果实跑发现 Claude Code 自己会调用辅助的小模型，再改成白名单，但 `implement` 的模型永远不在里面。误拦的结果是停下问你，不是放行。
      - 比较前把键规范化（去掉 `[1m]` 这类后缀），免得写法不同被误拦。同一个规范化也用在 `resolve_models` 的 `:178`（review 和 implement 不能是同一个模型）和 `:180`（fallback 不能是 implement 的模型），免得一边写全名、一边写别名或带后缀时被当成两个模型；`models.toml` 只允许完整的模型 id（第五轮评审第 2 条）。
      - review 和 implement 配成同一个模型的情况，`resolve_models`（`orc/bin/orc:178`）在 mission 开始时已经拒绝，不用另加。
      - **第 3 个 PR 合并前先实测**：在这台 Mac 的 CLI 上用和 orc 完全一样的参数各跑一次「不给工具」和「只给 Read」，把 `modelUsage` 的键记下来做测试样本，白名单按实测定。

## 第四版的独立评审意见（2026-11-14）

评审对象是 `0d6700f`，行号以 `f2682fb`（#19）为准。结论：「回到整体评审」和修复闭环、重新打开的状态机不冲突；`modelUsage` 的严格写法方向对（误拦时是停下问人，不是悄悄放行），但上线前要先实测。有一处要改：撤回不能挪进 `run_submit`。按严重程度排列。

### 1.【要改】撤回不能放进 `run_submit`

- `run_submit` 是后台任务：`cmd_gate` 只写 `result.json`（`orc/bin/orc:2556-2620` 里没有 `m.append`），不拿生命周期锁；STATE「后台任务和事件」定的是「任务自己跑，下一次 `orc step` 读到结果，在锁里写 `job-exit`」。
- `withdraw_reopen`（`:3943-3963`）要改两份 `state`、删 `unresolved-rework`、`parked`、`repair.json`、`reopen-prev`，还写 `node-withdrawn` 事件。放进后台任务，就是在锁外改状态、写事件，和 broker、`integrate-task.sh`（它们在锁里读这些文件）抢。
- **要改：** `run_submit` 发现「有 `reopen-prev`、HEAD 等于基线」时，不评审，只返回一个结果（比如 `outcome: "unchanged"`）；由 `orc step` 在锁里处理这个结果时调用 `withdraw_reopen`。

### 2.「回到整体评审」和状态机：不冲突（核过）

- **分流的位置：** `launch_integrate` 由 `orc step` 在锁里调用（第 5 步 `:3002-3009`，以及 `resume == "integrate"`）。HEAD 不等于最近一次 aligned 的 `head` 时调用 `launch_submit`（写 `job-start`），节点仍是 submitted；评审 aligned 后，第 5 步再走到 `launch_integrate`，这次 HEAD 对得上。不要在 `launch_integrate` 里直接跑评审。
- **测试修正那条路：** `sync_to_tip` 同时把基线改成 tip（`:3892` 起），重新评审的 diff（基线..HEAD）仍然只是节点自己没集成的改动；检查按新测试重跑，正是需要的。
- **修复闭环：** `repair.json` 只在提交关口起作用，整体评审不受影响；重新打开的节点照常走提交关口 → 整体评审 → 集成。
- **drift 计数：** 重新评审发生在一次 aligned 之后，「从上一次 aligned 以来连续」自然从 0 开始，不会因为这次分流多算一次。
- **建议（次要）：** 分流时记一条事件（比如 `integrate-deferred`，带旧 `head`、新 HEAD、原因），状态页和事后排查能看到为什么又评审了一次。

### 3.【要改】`FINAL_ROUNDS` 要拆成两个

- `reopen_for` 对最终审查和跨 mission 评审用的是同一个常量（`:3466-3467`，`streak > FINAL_ROUNDS`；`final_streak` 按类型分开计数，`:3452-3461`）。
- 只把 `FINAL_ROUNDS` 改成 1，跨 mission 评审也会变成 1 轮，和「跨 mission 评审仍是 2 轮」矛盾。
- **要改：** 第 3 个 PR 里拆成两个常量（偏离评审 1、跨 mission 2），列进要改的地方；`STATE.md:284`「最多打回 2 轮」跟着改。
