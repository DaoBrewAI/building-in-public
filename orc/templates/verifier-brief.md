## 要产出的东西

1. **测试文件**：写在 `repo/` 里，用产品仓库已有的测试框架和约定。规则：
   - 只能**新建**文件，不能改 `repo/` 里已有的文件。
   - 不能和任何节点的 `files` 重叠（执行会话要改那些文件；测试必须是它改不了的）。
   - 只通过 `contracts` 和设计里写明的接口去测，不依赖内部实现细节。
   - 断言要具体：边界值、错误输入、设计里写明的行为都要覆盖，不要只测“能运行”。
   - 被测接口在**测试函数里面**导入，不要放在文件开头。接口还不存在时，应该是这条测试在断言或导入处失败，而不是整个文件在收集阶段就报错：收集阶段报错时一条断言都没运行，证明不了测试测得对。
2. **`checks.json`**，写在工作目录根上（不是 `repo/` 里）：

```json
{
  "version": 1,
  "mission": "{{MISSION}}",
  "test_files": ["repo 相对路径，列出你新建的全部测试文件"],
  "checks": [
    {
      "id": "小写字母数字和 -，全局唯一",
      "node": "DAG 节点 id",
      "acceptance": [1],
      "command": "在仓库根目录直接运行的命令，例如 python3 -m pytest -q tests/test_x.py::test_y",
      "expect_before": "fail"
    }
  ]
}
```

   - `acceptance` 写这个检查覆盖该节点第几条验收标准（从 1 开始）。**每个节点的每条验收标准至少要有一个检查。**
   - `expect_before`：在现在的代码上（还没实现）这个检查应该 `fail` 还是 `pass`。测新行为的检查必须是 `fail`；只有验证“已有行为没有被破坏”的检查才写 `pass`。每个节点至少要有一个 `fail` 检查。
   - **检查挂在哪个节点上**：节点做完时，orc 只在这个节点和它的前置节点（`depends_on`，层层往上）都做完的代码上跑它的检查。所以挂在节点 X 上的检查，只能依赖 X 和它前置节点的改动；它运行到的测试里，不能有要等别的节点做完才会通过的。跑整套测试这类覆盖面大的检查，挂在依赖了所有相关节点的那个节点上；没有这样的节点，就只跑本节点的测试文件或测试函数。挂错了，节点永远完成不了。
   - **测试只导入本节点和前置节点的文件**：orc 会查每个检查跑到的测试文件（连同它导入的其他测试文件、上层目录的 `conftest.py`）里的每条 `import`：用到别的节点新建的文件（不是这个节点的前置节点），就退回给你重写；之后还有一个模型复核运行时才导入的写法（例如把 `"模块:名字"` 字符串交给会导入它的代码）。和前置节点并行的节点做的东西（例如另一个节点写的假实现），不能拿来用；需要替身就在测试里自己写一个。
   - 检查在沙箱里运行：不能联网，只能写仓库目录和临时目录。

orc 会在一份干净的当前代码上，只放入你列出的测试文件，逐条运行检查：`fail` 的必须失败，`pass` 的必须通过。用 pytest 的 `fail` 检查必须**失败在测试上**：退出码是 1，并且输出里有「N failed」。收集阶段报错（退出码 2）、找不到测试（4、5）、pytest 没有运行，都不算。不符合就把输出发回给你修。
