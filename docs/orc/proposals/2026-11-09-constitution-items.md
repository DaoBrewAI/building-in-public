# 提案：从 Neo 的「排查宪法」里拿两条进 orc

状态：**已定**（林翰 11-09：下面 6 条全部按推荐）。依赖 #19（修复闭环）：第一条改的是 #19 新增的诊断会话和修复关口，#19 合并后再动代码。

11-09 林翰让 orc 这边看 Neo 的宪法工具包（fintelli 仓库 `codex/rebuild-guards` 分支，`docs/rebuild-2026-11-05/constitution/`），判断哪些该进 ORC 工具箱。结论：工具包里的 6 个文件都不进；宪法 7 条里第 4 条（一个毛病查一类）和第 5 条（汇报写测了什么、没测什么）改写后进 orc。理由逐项写在最后一节。

## 一、诊断要列出同一根因的每一处（宪法第 4 条）

### 现在的问题

诊断会话（`templates/diagnose-brief.md`）只交根因、要改的文件、改法、证据和复现。它找到失败的那一处就停了。同一个根因如果还在别处（例如两个地方都先写状态、后写结果），修复只改了报上来的那一处，另一处下次再出问题，又要走一遍诊断和修复。修复关口和修复评审都只核对「改的是不是诊断说的那件事」，不会发现漏掉的同类。

### 提议

1. **诊断的输出加两个字段：**
   ```json
   "siblings": [{"file": "同一根因的另一处", "line": 行号, "fix": true | false, "why": "fix 为 false 时：为什么不用改"}],
   "sibling_search": "怎么找的：搜了哪些写法、看了哪些文件"
   ```
   没有同类就写 `"siblings": []`，`sibling_search` 照样必填。不许只写「没有」：要写清楚是怎么搜的，复核的人才能判断搜得够不够。
2. **orc 确定性核对**（放进 `diagnosis_problems`，和现在核对 `evidence` 一样，不过就发回诊断重写）：
   - `sibling_search` 不能为空；
   - 每一处的文件和行号在诊断时的提交上确实存在；
   - `fix` 为 true 的那一处，文件必须在 `files` 里（于是修复会打回这个文件所属的节点；跨了几个节点就是现有的多节点修复）；
   - `fix` 为 false 的必须写 `why`。
3. **修复评审多核对一件事**（`templates/repair-review-brief.md`）：诊断列出的同类，`fix` 为 true 的每一处都改了；`fix` 为 false 的理由站得住。
4. **同类在不属于任何节点的文件里**（mission 之前就有的代码）：这个 mission 改不了它（修复只能改节点的文件，这是底线）。见第 2 条决定。
5. **只在产品仓库里找。** 宪法原文是「在所有仓库里搜」，但诊断会话手里只有 mission 分支的代码副本，看不到别的仓库。跨仓库的同类留给人或者云端会话。

### 为什么这样做符合 orc 的规则

- 「列出同类」本身还是模型的判断（找得全不全，orc 判断不了）；orc 只确定性地核对能核对的部分：引的行存在、要修的在 `files` 里、理由不为空。这和 #19「默认做法由模型判断，底线由 orc 核对」一致。
- 不放宽任何底线：要修的同类仍由文件所属的节点来修，仍过修复关口（连跑 10 次、撤掉修复要失败、不许判断是不是在跑测试、修复评审）。

## 二、PR 正文第一段写测了什么、没测什么（宪法第 5 条）

### 现在的问题

orc 开 PR 时，正文只有请求原文和一句「全部节点已集成、最终审查通过」（`ensure_pr`）。哪些检查跑了几次、哪些没跑、哪些只是评审判的、哪些要人亲手验收，都在 `events.jsonl` 里，PR 上看不到。phase 结论里有 `needs-human`，但 mission 的 PR 没有。

### 提议

PR 正文的第一段改成两张清单，**由 orc 从事件记录里生成，不让模型写**（会话自己报的「测了」只是一句话，不是证据）：

- **测了**：
  - 每个冻结的检查：命令，最终审查各跑 3 次的结果；
  - 修复闭环里每次修复：修复后连跑 10 次的结果、撤掉修复后有没有失败（来自修复关口的记录）；
  - 跨 mission 评审、最终审查的结论；
  - CI：`verify` 和隐藏考题（只有通过或失败，以及没过的条款号）。
- **没测或没证明**：
  - orc 记录里明确跳过的步骤（例如测试文件太长，「测试越过依赖」的评审跳过了）；
  - 修复关口里没证明的修复（多节点修复、没有可重跑的检查）；
  - 「已被之前的提交满足、不用再改代码」的验收标准：只跑了对应的检查，没有新的改动；
  - 没有对应检查的部分：DAG 里每个节点的 `verification` 是命令，命令测不到的（真浏览器、真设备、部署后的站点、真实模型的效果）orc 不知道。现在 DAG 没有「要人亲手验收」这一项，所以这一行先固定写「冻结检查之外的行为没有测」；phase 结论里已经有 `needs-human`。要不要在 DAG 里加这一项，另外提。

PR 是在 CI 跑之前开的，所以开 PR 时 CI 那一行写「等待中」；CI 有结果后 orc 用 `gh pr edit --body` 更新这一段（见第 4 条决定）。

## 三、工具包里不进 orc 的部分，和原因

| 项 | 不进的原因 |
| --- | --- |
| `commit-msg` 钩子 | 它的装法 `git config core.hooksPath .githooks` 是仓库级设置，会盖过全局的 `/opt/northstar/git`，这个仓库里检查 `[N#]` 的 commit-msg 就不跑了。agent 也执行不了这条命令（northstar 的 `guard.sh` 拦含 `core.hooksPath` 的命令）。orc 自己提交用 `core.hooksPath=/dev/null`，钩子本来就拦不到 orc 的提交，真正起作用的是 CI。本机想装的话，位置是 `.git/hooks/commit-msg`，northstar 的钩子会接着调用它。 |
| `block-no-verify.sh` | `guard.sh` 已经拦 `--no-verify` 和 `core.hooksPath`，由托管设置注册，对 Claude Code 和 Codex 都生效。Neo 的版本更弱（11-09 实测）：`git commit -nm x`、`git -c core.hooksPath=/dev/null commit -m x` 都放行；`git commit -m x && head -n 5 f` 这种正常命令反而被拦。 |
| `session-constitution.sh` | `~/.claude/CLAUDE.md` 本来就在开局和压缩后加载，再注入一遍是重复。装在用户设置里，orc 的每个 `claude -p` 会话也会被注入，签名的 brief 之外多出一段文字。 |
| `ci-step.yml` | 核心仓库已经机器检查「根因」（`.northstar/checks/core_checks.py` 的 `commit_root_cause`，经 seal），并放过 `[NS]`、orc 冻结测试的提交和只改豁免路径的提交。Neo 的步骤没有这些豁免，orc 冻结测试的提交没有那四行，每个 orc PR 的 CI 都会红。要加「同类」就改 `core_checks.py` 那个正则（经 seal）。「测了 / 没测」不按提交要求：会话自己写的一行字，机器只能查它存在，查不了真测过；放在 PR 上、由 orc 从记录生成（第二节）。 |
| `settings-hooks.json` | 只是注册上面两个钩子。 |
| 宪法第 2 条（理解归模型，保证归代码） | 讲产品里模型和代码的分工，属于产品仓库的范围宪法（Neo 的 README 2.10 已经分别写了核心和税务包的）。 |
| 宪法第 3、6、7 条 | orc 已经由程序保证：执行会话觉得测试不对只能停下申诉或回 `outside`，测试的修正要用户签名；冻结测试、hub 里的考题、诊断、修复评审都由没写代码的会话做；「底线写死」就是第 7 条。 |

## 四、宪法放进全局 `~/.claude/CLAUDE.md` 时要注意的

这不是 orc 的改动，是林翰自己装宪法时要知道的：orc 的 `claude -p` 会话也会读全局 `CLAUDE.md`。宪法末尾要求「每份排查报告固定八栏」，而 orc 的诊断、评审会话最后必须只输出一个 JSON 对象。模型照八栏写，orc 解析不了，这次诊断就记成「不可用」，问用户。

## 要你定的

**林翰 11-09 定：6 条全部按推荐。** 下面保留原来的选项，供以后查。

1. **诊断要不要列同类**：推荐要（第一节）。备选：先不加，只在修复评审里让评审会话顺带看有没有漏掉的同类（不强制，核对不了）。
2. **同类在不属于任何节点的文件里**：推荐不拦，orc 把它写进 PR 正文的「同类，不在这个 mission 里」，你决定要不要另开 mission。备选：当成 `design`，停下问你（会挡住这个 mission）。
3. **同类在别的节点的文件里、诊断判断不用改**（`fix: false`）：推荐允许，但要写 `why`，修复评审核对理由。备选：同类一律要改。
4. **PR 正文什么时候更新**：推荐开 PR 时写本地的结果、CI 那一行写「等待中」，CI 有结果后 `gh pr edit` 更新。备选：等 CI 有结果再加一条 PR 评论，不改正文。
5. **「测了 / 没测」谁写**：推荐 orc 从事件记录生成，不让模型写。没有备选：让模型写就是会话自己报，不算证据。
6. **全局宪法**：推荐你装之前，在「八栏」那句前加一句「工具规定了输出格式时（例如 orc 要求只输出 JSON），以工具为准」，再在一个测试 mission 上跑一次诊断确认能解析。备选：先不放进全局，只放进各产品仓库的 `AGENTS.md`（orc 的会话在产品仓库的副本里也会读到，同样要加那一句）。
