# 提案：orc 的修复闭环（底线写死，修 bug 时由模型判断）

状态：**林翰 2026-11-08 和 Claude 讨论后定下方向**（下面「已经定了的」）。要林翰逐条确认的是「规则分两类」那张表，确认后再动手实现。起因是 `fintelli-p1-1-3` 卡在最终审查。

## 发生了什么

`fintelli-p1-1-3` 的 10 个节点都集成了，最终审查跑整套测试时，`test_app_say.py::test_fake_processor_reaches_each_status[done]` 失败。

- **问题在 intake-fakes 写的 `fake.py`。** `done` 先报版本、后报消息「fake done」。状态由已报的事实现算（N13），一出现版本就是 done。测试轮询到 done 立刻核对消息，常常读到空值。执行会话单独跑了 30 次，失败 11 次。
- **前面几道关口都是碰巧通过的。** intake-app 的提交关口跑了一次这个测试，最终审查里同一个检查也跑了一次，都过了。intake-fakes 自己的测试是同步调用假处理器，碰不到这个先后顺序。
- **orc 打回错了节点。** 失败的检查 `intake-tests-core-suite` 归 intake-tests，orc 就打回 intake-tests。可 `fake.py` 归 intake-fakes，intake-tests 改不了，只好停下来问用户。用户回答「去改」也没用：执行会话仍然只能改自己声明的文件。剩下的出路只有放弃这一轮，前面 9 个节点的工作全部作废，从头规划、重写测试、重写代码、重新签名、重跑 CI。

## 根因

真实运行以来出过的问题分两类。

**第一类：一次性的接入问题。** 检查副本没有 `.git`、提交说明要写「根因」正文。都是 orc 第一次接触真实仓库时，环境或约定和产品仓库没对上。修一次就好，以后不会再出现。

**第二类：同一个结构问题反复出现。** 发现问题的节点和能修问题的节点不是同一个。

| 哪次 | 在哪发现 | 该谁修 | orc 当时能做什么 |
| --- | --- | --- | --- |
| `subtract`（trial） | 跑整套测试的检查挂在了前置节点上 | 检查挂错了节点 | 节点永远完成不了；后来在 brief 里加了一条规则 |
| `fintelli-p1-1-2` | intake-service 的提交关口 | 测试本身用了并行节点的文件 | 只能放弃重跑；后来加了三层依赖检查（#18） |
| `fintelli-p1-1-3` | 最终审查，算在 intake-tests 头上 | intake-fakes 的 `fake.py` | 打回 intake-tests，它改不了，停下问用户 |

每次的做法都是：在前面多加一道拦截，挡住这一种情况。下次换一种跨节点的问题，又会卡住。

**根子在于 orc 擅长预防，不擅长纠错。** 前半段很严：签名的计划、实现之前就冻结的测试、文件归属、每个提交都要过关口。但它默认「计划和测试是对的，出了问题就是失败检查所属节点的问题」。

- 打回给谁，按「失败的是谁的检查」定；谁能改，按「文件归谁」定。两者不一致时，没有任何一步去判断「这个问题该谁修」。
- 所有规则一律写成硬性规则。其中有些是不能突破的底线，有些只是平时的默认做法，orc 没有区分。
- 出路只有「问用户」和「放弃」。可用户的回答只会作为文字转给同一个受规则约束的会话，用户手里同样没有能起作用的动作。这就成了死循环。

预防不可能挡住所有问题，计划和测试又是模型写的，每一轮都不一样。系统要稳定，靠的是纠错闭环，而不是越加越多的拦截。

## 已经定了的（林翰 2026-11-08）

1. **执行阶段不变。** 节点只改自己声明的文件，防止并行时互相踩踏。
2. **修 bug 阶段可以变通。** 诊断会话决定该改什么，修复会话照做，可以改诊断指定的、属于别的节点的文件。
3. **修复要满足这些约束：**
   - 改的文件不超出诊断指定的范围；
   - 评审核对改动确实是诊断说的那件事，而且没有改变别的节点承诺过的行为；
   - 撤掉修复后，失败必须能重现；
   - 全部检查和 NORTHSTAR 检查都要通过；
   - 非测试代码里不能有判断「是不是在跑测试」的写法；
   - 每一步都留痕。
   - **不按改动行数设上限。** 行数说明不了改得对不对。
4. **改冻结的测试必须用户签名。** 修 3 轮还过不了才找用户，找的时候附上 orc 能直接执行的选项。
5. **orc 只问能直接执行答案的问题。** 每个选项都对应一个 orc 马上能做的动作。
6. **最终审查时每个检查跑 3 次，任何一次失败都算失败。** 这样能提早抓到偶发失败。

## 规则分两类（要林翰逐条确认）

**底线**：写死，确定性核对，任何阶段都不能破。**默认做法**：平时照做，修 bug 时由诊断会话判断要不要变通，orc 再核对结果有没有守住底线。

| 规则（STATE.md） | 分类 | 修 bug 时 |
| --- | --- | --- |
| 计划、设计、DAG、冻结的测试和检查由用户签名，哈希逐一核对 | 底线 | 不变 |
| 冻结的测试只读（哈希一致） | 底线 | 不变；要改测试走下面的「测试本身有错」，用户签名 |
| 不越出签名的 mission 的 `scope` / `forbid` | 底线 | 不变；修复改的文件也要在 scope 里 |
| NORTHSTAR 签名有效，`.northstar/checks/run_all.sh` 通过 | 底线 | 不变 |
| 每个提交先过检查、再过对齐评审；评审不降级，出错时不放行 | 底线 | 不变；修复提交另加下面的「修复关口」 |
| broker 用 `diff_sha256` 绑定评审过的改动 | 底线 | 不变 |
| 沙箱：不联网，只能写自己的 worktree 或副本，产品仓库的 git 只读 | 底线 | 不变 |
| 不改写历史；PR 由用户合并；CI 的 `verify`、`exam` 必须通过；隐藏考题对会话不可见 | 底线 | 不变 |
| 进入 `accepted` 前从协议文件重新核对 | 底线 | 不变 |
| 节点只改自己声明的 `files` | 默认做法 | 执行阶段照旧；修复时按诊断指定的文件 |
| 最终审查时，冻结检查失败就打回检查所属的节点 | 默认做法 | 改成交给诊断会话判断 |
| `run_all.sh` 失败、落不到节点，就停下 `mediate` | 默认做法 | 改成交给诊断会话判断 |
| 执行会话说测试有错，review 模型认为确实有错时，只能回到验证这一步，重新审阅、go、签名 | 默认做法 | 改成：诊断会话写好测试的修正，用户签名后接着跑，已集成的工作保留 |
| 最终审查最多打回 2 轮 | 默认做法 | 改成修复闭环最多 3 轮 |
| 提交关口连续被拒 3 次就 `mediate` | 默认做法 | 不变（执行阶段的事） |
| CI 失败后，回答只会让 orc 重新等 CI | 默认做法 | 改成：用户看过考题输出后给一句提示，作为诊断的输入，进入修复闭环；或者选择放弃 |

## 修复闭环

**什么时候进入：**
- 最终审查里有检查失败（冻结检查或 `run_all.sh`）；
- 最终审查的模型判不通过；
- 提交关口失败，而原因在本节点声明的文件之外（#18 的第 3 层就属于这种，以后不再直接让用户放弃，而是进入这里）；
- 执行会话提问或说测试有错，而要做的事超出了本节点能改的范围。

**1. 诊断会话（`review` 角色，Fable；只读，不改代码）**

先由 orc 准备事实：失败的检查在当前 tip 上重跑 10 次，记下失败几次（偶发还是必然）；mission 分支上每个文件由哪个节点提交、最后改动在哪一行。

再把以下材料交给诊断会话：失败的输出、上面的事实、mission 的完整改动、签名的设计、DAG（每个节点的约定和验收标准）、冻结的测试全文。

它输出：

```json
{"kind": "code" | "test" | "design",
 "cause": "根因，一两句话",
 "files": ["要改的文件"],
 "change": "要怎么改（意图，不是代码）",
 "test_fix": "kind 为 test 时：测试改成什么、为什么"}
```

orc 对诊断做确定性核对：
- `files` 里的文件都在 mission 的 scope 里，不在 forbid 里，也不是冻结的测试（`kind` 为 `code` 时）；
- `cause` 里提到的文件和行确实存在。

核对不过，就把问题发回诊断会话；修 2 次还不对，才找用户。

**2. 按诊断结果分三条路走**

- **`code`（实现有 bug）：** 新开修复会话（`implement` 角色，Opus），只放行诊断指定的文件。它在一个从 mission tip 开出的修复 worktree 里改，提交走下面的修复关口，过了就合进 mission 分支，再做一次最终审查。**不找用户。**
- **`test`（测试本身有错）：** 诊断会话写好 `test_fix`，orc 把测试的改动和理由做成一页给用户看，并更新冻结测试的哈希。用户运行 `northstar approve-mission` 签名（一次 Touch ID），orc 核对签名后接着跑，已经集成的工作保留。签名覆盖的是更新后的整套文件。这一步要实测 `approve-mission` 在执行中途能不能重新签。
- **`design`（计划或设计有问题，不是 bug）：** 停下问用户。可选的动作只有两个：放弃这一轮，或者按诊断的说明 `orc revise`。

**3. 修复关口**（修复提交在原有提交关口之外，还要多过这些）

- **文件：** 改的文件 ⊆ 诊断的 `files`。确定性检查。
- **证明修好了：** 失败的检查在修复后的 tip 上连跑 10 次，全部通过；撤掉修复，回到修复前的 tip（第 1 步已经跑过 10 次），失败必须至少出现一次。这是确定性检查。
- **全部检查：** 冻结检查和 `run_all.sh` 全部重跑并通过。
- **不许判断是否在跑测试：** 修复改动的非测试代码里，不能出现 `pytest`、`PYTEST_CURRENT_TEST`、测试文件名，也不能新增 skip 标记。确定性扫描。
- **评审（`review` 角色）：** 拿到诊断、修复改动，以及被改文件所属节点的约定和验收标准，回答两个问题：这处改动做的是不是诊断说的那件事，有没有改别的？有没有改变这些节点承诺过的行为？
- **留痕：** 诊断、改动、修复前后各跑了几次、评审结论，单独写进状态页和 PR 说明里的「修复」一节。

**4. 上限**

修复闭环最多 3 轮。第 3 轮还过不了，就停下问用户，附上每一轮的诊断和结果，选项是：再给一轮并附上你的提示，或者放弃。

**5. 最终审查每个检查跑 3 次**

任何一次失败都算失败。整套测试只要几秒钟，代价很小，能把偶发失败提前抓出来，不再靠运气通过。

## 不变的

- 执行阶段的调度、节点隔离、提交关口、整体评审、集成，全部不变。
- 签名和信任层不变；冻结的测试仍然只有用户签名才能改。
- 隐藏考题仍在 CI 里跑，所有会话都看不到它。它是最后一道防线：修复会话即使骗过了所有冻结测试，也过不了它。

## 对正在跑的 `fintelli-p1-1-3`

它停在 intake-tests 的提问上，前 9 个节点的工作都是好的。修复闭环合并以后，回答这个提问、让它进入修复闭环就行，不用重跑。诊断会话应该会判定是 `fake.py` 里两行的先后顺序；修复会话调换两行，关口里连跑 10 次全部通过，撤掉修复又能重现失败，最后合并。
