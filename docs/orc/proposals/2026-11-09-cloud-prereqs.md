# 提案：mission 开工前要准备的东西，交给云端会话自动做

状态：**草稿，等林翰定**（下面 7 条）。

林翰 11-09 提的：设计文档写完、phase 分好之后，每个 mission 开工前都要准备评审、测试和隐藏考题。考题让云端的 Fable 或 Opus 写都可以。希望说一句「按 orc 的标准把准备工作都做掉」，就自动开云端会话去做，不用自己一个个开。

## 现在每样准备工作在哪里做、谁做

| 准备工作 | 现在谁做、在哪里 | 什么时候 |
| --- | --- | --- |
| NORTHSTAR、画布（`architecture.json`） | 你写、签名 | 每个产品一次 |
| phase 文档的依赖表 | 你写 | 每个 phase 一次 |
| mission 的设计和 DAG | orc 的规划会话，本机 | mission 开始时（依赖的 mission 合并之后） |
| 冻结的验收测试 | orc 的验证会话（`review` 模型），本机 | 规划之后、go 之前 |
| 审阅页、go、签名 | 你读、你签（Touch ID） | 每个 mission 一次 |
| 隐藏考题 | **你自己写**，放在 `DaoBrewAI/LY_orchestrator-hub` 的 `exams/<仓库>/run.sh`；CI 用 secret `NORTHSTAR_EXAM_TOKEN` 取 | 现在没有固定时间点 |
| 独立评审 | PR 的评审由云端会话做（11-09 定：所有评审都开云端会话）；mission 的计划在 go 之前没有独立评审 | 合并前 |

本机的那几样已经是自动的：`orc phase` 依赖满足就开始 mission，规划、写测试一路跑到审阅页，停下等你 go。真正要人手动开会话的是**隐藏考题**，其次是 **go 之前的独立评审**。所以这个提案只把这两样搬到云端，其余不动。

## 为什么考题和评审能上云端，规划和测试不能

- 规划、写测试要用本机的 `~/.orc`（mission 的状态、签名的 control 目录）和沙箱，结果要进签名链；云端会话碰不到这些，也不该碰。
- 签名（`northstar seal`、`approve-mission`）要你的 Touch ID，谁都代替不了。
- 考题**必须**不在本机写：本机执行会话用的 agent token 读不到 `LY_orchestrator-hub`（11-08 核实是 404），考题就靠这个和执行会话隔开。云端会话用的是 claude.ai 上你的 GitHub 连接，是另一个身份。
- 评审本来就该独立于写代码的会话，云端正好。

## 提议

1. **触发点是 go。** 你对某个 mission 说 go、签完名，coordinator（orc skill）就为这个 mission 开一个云端会话写考题。考题只在 CI 用到，执行不用等它。
   - 不在 phase 一开始就把所有 mission 的考题写完：考题要按设计里定下的接口来测，而 mission 的设计要等它依赖的 mission 合并后才写。
2. **考题会话**（Fable，`review` 角色，和执行用的 Opus 不同）：
   - 给它：NORTHSTAR 里这个 mission 的条款原文、签名的 `design.md`、DAG（每个节点的约定和验收标准）、产品仓库的地址。这些都不是秘密，orc 从 control 目录读出来，写进会话的提示词（云端会话读不到本机的 `~/.orc`）。
   - 不给：冻结的验收测试。考题是另一份独立的检查，照着条款和设计写，不照着测试写。
   - 它在 `LY_orchestrator-hub` 开一个分支、提一个 PR，把这个 mission 的考题加进 `exams/<仓库>/`，按 STATE.md「PR 和 CI」的约定报条款（`N13 fail`）。不在产品仓库留任何东西，不在任何公开的地方贴考题内容。
   - 你看一眼 PR、合并。
3. **orc 怎么知道考题好了**：orc 读不到 hub（这是故意的），所以在开产品 PR 之前问你一句「这个 mission 的考题合并进 hub 了吗」。你回答之前，orc 不开 PR。
4. **go 之前的独立评审**（可选，见第 7 条）：审阅页生成时，coordinator 开一个云端会话评审这个 mission 的设计、DAG 和冻结的测试。它看不到规划过程。评审结果发回 coordinator，和审阅页一起给你看，你再决定 go。
5. **怎么开云端会话**：coordinator 在产品仓库（例如 daoharness-core）的会话里，用开会话的工具开云端会话，提示词里带上第 2 条的材料。云端会话做完可以把结果发回 coordinator：11-09 云端的评审会话就是这样把 review 结果发回来的。

## 已经核实的和还没核实的

- 已核实：考题的位置和 CI 取考题的方式（同上）；本机 agent token 读不到 hub；云端会话能把消息发回本机会话（11-09 实际发生过）。
- 没核实：
  - **从本机会话开云端会话不一定成功。** 11-09 在 orc 的 worktree 会话里试了两次都被拒（一次是 app 没认出这是 GitHub 仓库，一次是指定仓库后要求重新加载窗口）。在 daoharness-core 的会话里还没试过。
  - **云端会话能不能往 hub 推送。** 已经有一个云端会话「写 DaoHarness 核心的隐藏考题」，但本机看不到它的记录，没核实它是怎么拿到 hub 的写权限的。
  - **routine（保存好的云端任务）。** 文档上它可以按需运行、定时运行、或由 GitHub 事件触发；但账号上现在只有一个绑在这台 Mac 上的 routine，云端的 routine 没跑过，也没核实按需运行时能不能每次传不同的 mission 材料。

所以第一步是实测：在 daoharness-core 的会话里开一个云端会话，让它往 hub 开一个只有说明文件的 PR。成功了再动 orc。

## 要你定的

1. **触发点**：推荐 go 之后，每个 mission 一个考题会话。备选：phase 开始时只按 mission 文件一次写完所有考题（接口还没定，考题容易测错）。
2. **考题用哪个模型**：推荐 Fable（和执行的 Opus 不同，PLAN 里评审也是这条规则）。备选 Opus。
3. **考题会话看不看冻结的验收测试**：推荐不看。
4. **考题怎么进 hub**：推荐开 PR、你合并（你能看一眼，不会悄悄改掉已有的考题）。备选：直接推到 main。
5. **orc 怎么知道考题好了**：推荐开产品 PR 之前问你一句。不推荐给 orc 读 hub 的权限：那样执行会话也可能读到。
6. **怎么开云端会话**：推荐 coordinator 用开会话的工具（每次带不同的材料，结果能发回来）。备选：routine（要先核实能不能每次传材料），或 GitHub 事件（例如 phase 文档合并进 main 时）自动触发（全自动，但时机和 go 对不上）。
7. **go 之前要不要加云端评审**：推荐加，结果只给你参考、不拦 go。备选：先不加，只做考题。

这条会改一个以前的做法：真实产品的隐藏考题以前是你在会话之外自己写，以后由云端会话写、你合并 PR。
