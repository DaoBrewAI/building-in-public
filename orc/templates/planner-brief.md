## 要产出的文件（都写在工作目录里）

1. `design.md`：设计。用户给了 PRD 或需求文档时，把它并进来。写清楚关键决定和理由；不写实现细节到代码层面。
2. `plan.md`：计划。分几步、每步做什么、风险在哪。
3. `task-dag.json`：执行用的任务 DAG，格式如下（每个节点由一个独立的执行会话完成）：

```json
{
  "version": 1,
  "mission": "{{MISSION}}",
  "tasks": [
    {
      "id": "short-id",
      "depends_on": [],
      "files": ["repo/relative/path.py"],
      "contracts": ["这个节点对外提供或依赖的接口"],
      "verification": ["能独立验证这个节点的命令，例如 pytest tests/test_x.py"],
      "acceptance": ["可验证的验收标准，一条一句"],
      "clauses": ["N1"],
      "component": "所属组件",
      "state": "ready"
    }
  ]
}
```

DAG 的规则：

- `mission` 必须是 `{{MISSION}}`；`state` 一律写 `ready`。
- `files` 写这个节点会改或新建的全部文件，用仓库相对路径。**没有依赖关系、可以同时跑的节点，`files` 不能重叠**。
- 每个节点要小：一个执行会话能在一次运行里做完，每条验收标准对应一次提交（一次提交最多 8 个文件）。
- `verification` 至少一条，必须是能在仓库里直接运行的命令。
- `clauses` 写这个节点服务的 NORTHSTAR 条款编号（N#）{{CLAUSES_RULE}}。

4. `northstar-constraints.md`（可选）：从你的设计里挑出**少数**“违反了就等于换了设计”的关键决定，每条一行，写成 `- N<编号>: <约束>`，编号接在现有 NORTHSTAR 后面。没有这类决定就不要写这个文件。
